# Координатор и устойчивое состояние

## Владельцы фактов

Агент сообщает статус и результат исполнения. Gate хранит принятие и доставку
запроса агенту. Расширение хранит выбор инструментов, привязку диалога,
намерение отправки и подтверждение доставки результата в чат.
Адаптер передаёт наблюдения страницы и ревизию источника ответа.
Панель отображает состояние координатора и передаёт изменения отдельных полей.

## Переходы

Чистая функция `WebCodexSession.transition` получает состояние и событие,
возвращает новое состояние и намерения внешних действий. Очередь `enqueue`
применяет результат. Единственный исполнитель использует сохранённое намерение.
Наблюдательное сравнение переходов с прежними фазами выполнено в стенде
до включения функции в рабочий путь. Стенды полного жизненного цикла проверяют
допуски, отправки и число операций после переключения.

| Событие | Состояние и намерение |
| --- | --- |
| call_received | Проверенный вызов ожидает исполнения либо одобрения |
| dispatch_intent | Ключ, аргументы, поколение координатора и разрешения сохраняются вместе |
| operation_status | Полученный статус и идентичность операции, конфликт идентичности блокирует продолжение |
| result_ready | Результат готов, при пользовательской паузе остаётся сохранённым |
| delivery_intent | Сохранено намерение доставки определённой операции в определённый сеанс |
| delivery_confirmed | Подтверждённая операция очищает только собственные поля ожидания |
| pause | Сохраняется предыдущая фаза, новые действия блокируются |
| resume | Проверяется возможность продолжения, согласие и неизвестный исход |
| stop | Сеанс остановлен, известные факты операции сохранены |

У исполнения и доставки есть отдельные `executionStatus` и `deliveryStatus`.
Публичная `phase` сохраняет совместимость панели. Коды причины используются
для восстановления. Старые сохранённые сообщения сопоставляются кодам при
миграции и на совместимом входе прежнего content-скрипта.

## Сохранение и прерывание

Авторитетный снимок `webcodexDurableState` хранится в `storage.local`.
Версия схемы, состояние и намерение передаются одним вызовом записи одного ключа.
Кэш в `storage.session` может содержать снимок либо указатель. Восстановление
сначала читает устойчивый снимок. Старые обычные и большие снимки мигрируются.
Неизвестная версия сохраняется для открытия совместимым кодом.
Текущая версия снимка — 2. Версия 1 принимается и мигрируется при сохранении.
Старая реализация с поддержкой только версии 1 сохраняет новый снимок
и блокирует работу с неподдерживаемым форматом.

Каждый экземпляр координатора имеет отдельный идентификатор. Намерение содержит
сеанс, ключ операции, ревизию ответа и редакцию разрешений. Перед отправкой
после ожиданий проверяется актуальность действия.

Пауза, отзыв согласия и смена диалога немедленно меняют локальную редакцию
разрешения новых действий. Запрос прерывания записывается отдельным последовательным
журналом до сигнала отмены UI. Основная очередь затем применяет его к снимку.
После перезапуска неприменённая запись снова блокирует продолжение.
Отзыв автоматического одобрения и выключение автоматической доставки имеют
отдельные редакции. Принятая агентом операция сохраняет возможность опроса.

Проверены потеря session-кэша, отказ записи до отправки, пауза во время записи,
получение результата после паузы, отзыв автоматического одобрения и восстановление
отзыва согласия до обработки очередью. Проверка перезапуска установленного
расширения в настоящем браузере входит в итоговую живую приёмку.

## Предпочтения

Новая панель передаёт имя изменённого поля. Координатор объединяет его
с последними сохранёнными значениями. Запись получает новую ревизию.
Панель сохраняет пользовательский ввод при опросах и отбрасывает более старые
снимки предпочтений. Совместимый полный запрос старой панели поддерживается.

## Журнал прямых операций

Локальный агент сообщает поддержку `operations/lookup` при подключении.
Расширение получает статус по сохранённому ключу, даже если ответ создания
потерялся до получения ID. Чтение выполняется через прежний адрес с проверкой
сохранённой идентичности агента. Старому агенту требуется обновление для такого
восстановления. Операция сохраняет исходный маршрут.

После `not_found` разрешена отправка прежнего намерения с тем же ключом
и аргументами. Перед отправкой повторно проверяются пауза, согласие
и разрешение автоматического выполнения. Для старого опасного намерения
без сведений об одобрении требуется действующее одобрение. Во время паузы
разрешено чтение статуса. Полученный результат остаётся в сохранённом сеансе.

Агент публикует целую синхронизированную запись резервирования перед эффектом.
Повтор ключа сравнивает имя инструмента и аргументы. Новые записи привязаны
к источнику, клиенту расширения и идентичности исполнителя. Совпадение ключа
с чужой областью даёт конфликт. Старые записи без области остаются читаемыми
на прежнем агенте для совместимости сохранённых операций.

Повреждённая запись, незавершённая запись прежнего процесса и ошибка сохранения
результата дают `outcome_unknown`. Сохранение результата в Windows допускает
совместное чтение и ограниченно повторяет атомарную замену при временной
блокировке файла. Повторяется файловая операция сохранения журнала.

Для проверки исхода команды доступны существующие `list_commands`
и `poll_command`, использующие отдельную историю команд агента.
Автоматическое повторное исполнение произвольного инструмента после
неизвестного исхода блокируется. Совпадение содержимого файла само по себе
не подтверждает, какой запрос его создал.

### Хранение и истечение

Записи и результаты сохраняются бессрочно. Автоматическая очистка отсутствует.
Отсутствующий ключ с меткой времени старше 24 часов получает `expired`.
Создание с таким ключом сохраняет запись истечения без запуска инструмента.
Найденный сохранённый результат доступен независимо от возраста ключа.
Старые непрозрачные ключи без метки времени сохраняют прежнюю совместимость.
Эти значения выбраны при реализации этапа 7. Удаление каталога операций
вручную уничтожает доказательства выполнения и защиту старых непрозрачных ключей.

### Проверки этапа 7

Проверены восстановление до получения ID, получение результата во время паузы,
пауза во время чтения отсутствующего ключа, старый агент, истечение, повреждение
записи, совместимость старого журнала, конфликт клиента и повтор аргументов.
Параллельное первоначальное резервирование проверяется двадцатью запросами.
Профильный набор Go повторён двадцать раз.
Общий набор JavaScript содержит 338 проверок, 333 прошли, 5 проверок
отдельных стендов пропущены. Прямой стенд с EXE запущен отдельно и прошёл.
Полные наборы четырёх Go-пакетов прошли. Проверки остановки дочерних процессов
выполнены вне ограниченной среды, блокирующей `taskkill`.

Тест собранного EXE использует прямой HTTP, пустые настройки Gate и отдельный
временный каталог. Он проверяет потерю ответа до ID и восстановление после
перезапуска. Полная живая приёмка установленного расширения остаётся этапом 11.
Временный тестовый EXE находится в `tmp/stage7/webcodex-agent.exe`.
Релизный комплект ещё предстоит собрать на этапе 10. Пользователю сейчас
не требуется самостоятельная сборка или замена установленных компонентов.

## Локальные артефакты и файловые предусловия

Байты вложения сохраняются в `storage.local` под ключом `webcodexArtifact`
с суффиксом SHA-256. Снимок сеанса содержит имя, тип, размер, хеш, длину кодировки
и ссылку на артефакт. Старое вложение с данными внутри снимка переносится
при сохранении. Сначала записывается артефакт, затем публикуется снимок со ссылкой.

При первом чтении после перезапуска проверяются размер и SHA-256 артефакта.
При передаче используются блоки base64 до 65 536 символов. Content-скрипт
повторно проверяет размер и SHA-256 собранного `File` перед загрузкой.
Повреждённый или отсутствующий артефакт даёт явную ошибку. Сеанс сохраняет
результат и исходную операцию. Автоматические запросы исправления модели
при ошибке передачи отсутствуют.

Память передачи кэширует одно текущее вложение. Повторная передача и перезапуск
используют сохранённые байты. Чтение исходника у агента для восстановления
вложения не требуется. Полное текстовое чтение также сверяет присланные агентом
размер и хеш. Для фрагмента сохраняются исходный полный хеш, границы строк
и отдельный хеш передаваемых байтов.

Артефакты хранятся бессрочно. В расширении уже предусмотрено `unlimitedStorage`.
Достижение реального ограничения памяти или диска завершает запись ошибкой,
сохраняя прежний устойчивый снимок. Публикация ссылки выполняется после успешной
записи данных. Обязательные проверки охватывают пустые и бинарные файлы,
Unicode с CRLF, прежние границы 32 КиБ и 2 МиБ и восстановление большого вложения.

Изменения через файловые инструменты одного процесса агента сериализуются,
включая обращения разных исполнителей этого процесса. Ожидаемый хеш повторно
проверяется после подготовки временного файла перед каждой попыткой публикации.
После записи проверяется фактическое содержимое файла. Если результат записи
невозможно подтвердить, прямой журнал получает `outcome_unknown`.

Остаётся короткое окно между последней проверкой и заменой для внешнего
процесса, который меняет тот же путь. Обычные операции файловой системы
не предоставляют универсальную атомарную замену с условием SHA-256.
Проверки обнаруживают изменения перед публикацией и при проверке результата.
Для одновременных агентских записей с одним исходным хешем успешен один запрос,
остальные получают `stale_hash`. Проверено также изменение внешним редактором
после подготовки временного файла.

Короткие ссылки для модели на пути пока не добавлены. Пункт 7 этапа 8 связывает
их введение с измерением ошибок путей после основного синтаксиса. Хешированные
ссылки артефактов используются внутри расширения.

Тестовый EXE этапа 8 собран в `tmp/stage8/webcodex-agent.exe` и проверен через
прямой HTTP с пустой конфигурацией Gate, включая конкурирующие записи.
Пользователю сейчас не требуется заменять агент, Gate или расширение.
Готовый релизный комплект и инструкция перезапуска относятся к этапам 10–11.
Общий JS-набор этапа 8 содержит 341 проверку, 336 прошли, 5 стендовых
проверок пропущены. Прямой стенд с EXE прошёл отдельно. Все четыре Go-пакета
прошли. Файловые и журнальные регрессии дополнительно повторены десять раз.

## Последовательности сбоев прямого маршрута

На этапе 9 генератор запускает 36 последовательностей через настоящий
`local-client.js` и координатор расширения. Для каждого из трёх сбоев
используются начальные значения генератора от 1 до 12. Между ответом модели
и восстановлением перемешиваются перезапуск worker, опрос, пауза,
возобновление и повтор доставки того же ответа.

Проверяются потеря запроса до принятия, потеря ответа после эффекта до ID
и неизвестный исход. Во всех случаях сохраняются исходные байты, ключ
и прямой маршрут. Число побочных эффектов равно одному. Настройки Gate пусты,
обращений к Gate и автоматических переспросов модели нет.
При сбое тест печатает начальное значение генератора, тип сбоя и сокращённую
удалением событий последовательность. Начальный вызов и завершающая проверка
входят в каждый повтор.

Генератор выявил потерю диагностической причины при последовательности
«получить неизвестный исход, затем нажать паузу». Координатор теперь сохраняет
`outcome_unknown` и `operation_expired` при ручной паузе. Запрет возобновления
неразрешённой операции проверяется отдельно.

Исторический корпус, ошибки синтаксиса, маркеры, границы DOM, одинаковый текст
разных ответов, поздние события, отзыв разрешений и миграции покрываются общим
JS-набором. Дополнительно выполнены прямой HTTP со скомпилированным агентом,
Native Messaging со скомпилированным агентом и 80 сценариев в установленном
Chrome с изолированным профилем. Проверка настоящего AI Studio с установленным
расширением и общего preset для двух чатов входит в этап 11.
Общий набор этапа 9 содержит 343 проверки, 338 прошли, 5 стендовых пропущены.
Три проверки Chrome и EXE выполнены отдельно и прошли без пропусков.

## Проверка выпуска

`verify-release.ps1` запускает согласование версий, обычный JS-набор, свежие
тесты четырёх Go-пакетов и vet, сборку EXE, упаковку и полный набор обязательных
проверок с настоящим Chrome, агентом и тестовым Gate. В первом полном прогоне
этапа 10 прошли 343 теста без пропусков. ZIP проверяется по всем исходным байтам
и зависимостям. Две упаковки одних исходников дали одинаковый SHA-256.

Сведения о версиях берутся из `package.json`. Генератор синхронизирует
manifest, lock-файл, content-скрипт, клиентов и панель. Для кандидата выбраны
расширение `0.4.0` и агент `1.5.0-ai-studio-alpha.7`.

Манифест готовых файлов содержит исходный коммит, признак изменённых исходников,
версии, контрольные суммы, версии инструментов и результаты проверок.
Изменение исходников во время проверки или пропуск обязательного теста
завершает проверку ошибкой. Живая приёмка отмечается отдельно как этап 11.

Workflow `local-release-required` запускает тот же сценарий на Windows.
Проверка GitHub API от 14 ноября 2026 года подтвердила, что Actions включены,
main не защищена. Поэтому workflow сейчас сообщает результат проверки,
прямой push технически остаётся разрешён. Настройки защиты не изменялись.

# План делегирования простых задач Gemini

Дата: 16 ноября 2026 года. Статус: план; реализация ещё не начата.

## Что делаем

Основная модель в AI Studio получает новый инструмент `delegate_gemini`.
Она передаёт ему от одной до трёх независимых текстовых задач. Локальный агент
распределяет их между двумя или тремя ключами Gemini API и возвращает ответы
в исходный чат обычным результатом Helper. Модель объединяет ответы сама.

Модель исполнения — `gemini-3.8-flash`. Ключи пользователя принадлежат разным
аккаунтам и разным Google Cloud проектам: каждый ключ имеет отдельную квоту.
Это подтверждённое условие данной реализации, а не предположение, что любой
новый ключ даёт дополнительный лимит.

Первая версия работает только с переданным текстом. Субагенты не получают
прямого доступа к файлам, оболочке, истории чата или другим инструментам.
Для проверки кода основная модель передаёт необходимый фрагмент в задаче.
Ответ субагента — данные для основной модели, а не разрешение выполнять команды.

## Факты Google и ограничения

Проверено по официальной документации:

- Код модели — `gemini-3.8-flash`:
  [описание модели](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash).
- RPM — запросы в минуту, TPM — входные токены в минуту, RPD — запросы в сутки.
  Квоты применяются к проекту, а не к отдельному ключу. Суточный лимит
  сбрасывается в полночь по тихоокеанскому времени США:
  [лимиты](https://ai.google.dev/gemini-api/docs/rate-limits).
- Точные доступные квоты зависят от проекта и показываются на
  [странице лимитов AI Studio](https://aistudio.google.com/rate-limit).
  Открытая документация не задаёт универсальную гарантированную тройку
  RPM/TPM/RPD для бесплатного тарифа. Числа из форумов не выдаём за норму Google.
- Перед генерацией можно посчитать входные токены через `countTokens`:
  [учёт токенов](https://ai.google.dev/gemini-api/docs/tokens).
- Ключи связываются с проектами и должны храниться на стороне агента:
  [ключи API](https://ai.google.dev/gemini-api/docs/api-key).

Перед первым живым запуском записываем реальные RPM, TPM и RPD каждого проекта
из AI Studio. Без этих значений делегирование отключено с понятным объяснением;
остальные инструменты агента работают. Код не определяет бесплатный тариф
по виду ключа: пользователь проверяет тариф каждого проекта в AI Studio.
Локальный учёт не видит запросов из других приложений; ответ Google остаётся
окончательным источником сведений об исчерпании квоты.

## Настройка ключей

Файл `.env` лежит рядом с фактически запущенным `webcodex-agent.exe`.
Например, если EXE находится в `bin/aix`, файл нужен в этой же папке.
Путь определяется по исполняемому файлу, а не по текущей папке оболочки.
Существующий `.env` при установке и обновлении не заменяется.

Планируемые имена настроек:

| Имя | Назначение и значение |
| --- | --- |
| `GEMINI_API_KEY_1` | Первый реальный ключ пользователя; обязательный для включения делегирования |
| `GEMINI_API_KEY_2` | Второй ключ из другого проекта; используется при наличии |
| `GEMINI_API_KEY_3` | Третий ключ из третьего проекта; необязательный |
| `GEMINI_RPM_1`, `GEMINI_TPM_1`, `GEMINI_RPD_1` | Положительные целые значения трёх квот первого проекта из AI Studio |
| `GEMINI_RPM_2`, `GEMINI_TPM_2`, `GEMINI_RPD_2` | Те же квоты для второго проекта |
| `GEMINI_RPM_3`, `GEMINI_TPM_3`, `GEMINI_RPD_3` | Те же квоты для третьего проекта, если указан третий ключ |

В будущем `.env.example` будут только пустые поля и пояснения, без настоящих ключей.
Поддерживаем простой формат `ИМЯ=значение`, комментарии и значения в кавычках.
Не исполняем содержимое файла как команды и не подставляем переменные оболочки.
Файл читается при старте; для изменения ключей или квот нужно перезапустить агент.
Пустые/дублирующиеся ключи, повторяющиеся поля и неправильные квоты проверяем.
Ошибки указывают имя настройки, но никогда не её секретное значение.

Ключи не добавляем в окружение дочерних команд, состояние расширения,
аргументы инструментов, журналы, сохранённые задачи и результаты.
`.env` уже исключён из Git. Это не изоляция от разрешённого `exec_command`:
команда с правами пользователя может прочитать этот файл. Самим Gemini-субагентам
доступ к файловым инструментам и оболочке не выдаём.

## Инструмент и выполнение

1. Вход `delegate_gemini`: массив `tasks` из 1–3 объектов с уникальным `id`
   и непустым текстом `prompt`. Модель сама формулирует простые независимые задачи.
   Перед отправкой показывается обычное разрешение Helper для выбранного инструмента.
2. Агент проверяет весь вход до запуска: неизвестные поля, повторяющиеся ID,
   количество задач и размер текстов. В первой версии — до 32 КиБ UTF-8
   на задачу и до 4096 выходных токенов на ответ, с ограниченным временем исполнения.
3. Выбирает следующий доступный ключ по кругу: 1 → 2 → 3 → 1.
   На каждый проект одновременно выполняется максимум одна задача.
   Ключ без свободной квоты временно пропускается.
4. Если все ключи заняты или ждут минутную квоту, задачи остаются в очереди.
   При исчерпании всех суточных квот возвращается объяснение и время сброса,
   без ожидания до следующего дня внутри операции.
5. Одна операция содержит до трёх задач, которые могут исполняться параллельно.
   Во время её выполнения новые вызовы основная модель не обязана отправлять.
6. Ответ по каждой задаче: исходный `id`, статус, текст ответа либо понятная ошибка,
   фактическое использование токенов при наличии. Частичные успехи сохраняются.
   При блокировке ответа или достижении лимита вывода это явно указано;
   обрезанный ответ не объявляется полным.

Используем HTTPS REST API Google через стандартную библиотеку Go без нового SDK.
Ключ передаём в заголовке запроса, не в URL. Адрес API фиксирован;
автоматические перенаправления с секретным заголовком запрещены.
Не выводим исходные ошибки HTTP, которые могут содержать ключ или текст задачи.

## RPM, TPM, RPD и ошибки

- Планировщик общий для всех задач локального агента, с независимыми счётчиками
  по отпечатку ключа. Сырые ключи на диск со счётчиками не записываются.
- Резервирование квоты выполняется атомарно до отправки. RPM и TPM считаются
  в скользящем окне 60 секунд. Для входных токенов используем `countTokens`
  с тем же текстом и системной инструкцией, что и в генерации.
- Сам запрос подсчёта токенов также ограничиваем по частоте; пока его влияние
  на квоты конкретного проекта не подтверждено, консервативно учитываем его
  и в RPM/RPD. Не строим оценку TPM на правиле «четыре символа — токен».
- Если отдельная задача больше доступного TPM, возвращаем ошибку размера,
  вместо бесконечного ожидания. Повторная проверка и резервирование не дают
  двум параллельным задачам занять одну и ту же свободную квоту.
- Сохраняем суточные счётчики, недавние резервы и паузы проектов до отправки,
  чтобы перезапуск не обнулял квоты. Сброс суток учитывает переходы летнего времени
  в зоне `America/Los_Angeles`. Несколько процессов не должны независимо
  тратить один и тот же локальный бюджет: нужен единственный владелец журнала.
- При HTTP 429 учитываем указанный Google срок ожидания и тип исчерпанной квоты.
  Если тип не определён, останавливаем новые запросы этого проекта и сообщаем
  причину; не перебираем его повторно в быстром цикле.
- Для 401/403 отключаем ключ до исправления настроек, для недоступной модели
  возвращаем отдельную ошибку. Не переключаем модель на другую автоматически.
- Временные ошибки допускают ограниченные повторы с увеличением задержки
  и случайным разбросом, только после новой проверки квот. Сетевой тайм-аут
  после отправки может означать обработанный запрос: резерв не возвращаем,
  автоматически повторную генерацию не запускаем.
- Нельзя гарантировать общий лимит проекта, если тот же ключ используется
  другим приложением. Документируем это ограничение, обрабатываем отказы Google.

## Сохранение задач и работа чата

Переиспользуем существующие `operations/create`, `operations/get`,
`operations/lookup` и ключи идемпотентности. Второй независимый протокол задач не нужен.

Сейчас `studioOperations.create` выполняет инструмент синхронно, а локальный
HTTP-клиент ждёт примерно 15 секунд. Очередь и генерация могут занимать дольше.
Для `delegate_gemini` операция должна быстро сохраняться и возвращать ID со
статусом `running`; работа продолжается в фоне, расширение опрашивает тот же ID.
Это изменение ограничиваем новым инструментом, не меняем исполнение файловых команд.

Повтор запроса с тем же ключом возвращает ту же операцию. Перезагрузка вкладки
подключается к ней по ID и не повторяет генерацию. Результат каждой завершённой
подзадачи сохраняется сразу. После падения агента задача с неизвестным исходом
не отправляется в Google повторно автоматически; уже полученные ответы доступны.

Новый чат не получает ответы старого чата. Остановка/смена чата запрещает отправку
старого результата в него; уже принятая агентом операция завершает работу
в своём журнале. Отмена удалённой генерации в первую версию не входит.

В консоли сохраняем согласованный краткий формат:
`delegate_gemini — передаю 2 задачи Gemini` и затем
`delegate_gemini — готово 2 из 2`. Для ожидания квоты — редкое сообщение
с оставшимся временем. Ключи и полный текст задач не печатаются.

## Какие части проекта затрагиваются

| Часть | Изменение |
| --- | --- |
| `cmd/agent/` | Чтение выделенных настроек `.env`, клиент Gemini, планировщик, журнал квот и тесты; новые файлы рядом с существующим исполнителем |
| `cmd/agent/studio_native.go` | Фоновое выполнение новой операции и сохранение ответов подзадач с прежними проверками владельца и идемпотентности |
| `cmd/agent/tool_schemas.go`, `native_executor.go` | Схема и вызов нового инструмента; при отсутствии настроек он не предлагается модели |
| `cmd/agent/studio_console.go` | Короткие описания делегирования и результата |
| `ai-studio-extension/` | Проверка поддержки массива задач, опроса долгой операции и смены чата; новый инструмент выбирается существующей галочкой |
| Инструкции модели | Делегировать небольшие независимые задачи, передавать только нужный текст, анализировать ответы самостоятельно |
| `.env.example`, README и упаковка | Образец настроек без секретов, простая инструкция, включение образца в готовый комплект |

Делегирование отправляет данные внешнему API, поэтому не добавляем его в список
безопасных инструментов, включённых по умолчанию. Автоматическое выполнение
остаётся под действующими настройками выбранных инструментов и подтверждений.
Gate не получает ключи; первая версия предназначена для локального Helper.

## Этапы и критерии готовности

1. **Настройки и ограничения.** Реализовать чтение `.env`, проверки и планировщик.
   Проверить без реальных API-ключей: 2/3 проекта, чередование, конкуренцию,
   RPM/TPM/RPD, перезапуск, смену суток и повреждение журнала. При повреждении
   учёта не обнулять квоту молча.
2. **Запросы и долговечная операция.** Добавить текстовое делегирование и
   фоновые операции. Тестовый HTTP-сервер проверяет формат запросов, тайм-ауты,
   429, ошибки ключей, блокировки, обрезанные ответы и сохранение частичного успеха.
   Тесты подтверждают отсутствие секретов в логах, результатах и журнале.
3. **Чат и разрешения.** Проверить обычный путь Helper: до трёх задач,
   сохранение ID, переподключение, ручную доставку, запрет повторного выполнения,
   паузу, отзыв разрешения и переход в новый чат. Убедиться, что файловые команды
   и восстановление старых операций работают как прежде.
4. **Инструкция и сборка.** Описать каждое поле `.env.example`, выбор галочки
   и ожидаемый результат. Собрать новый агент и комплект, выполнить обязательные
   проверки выпуска. Каждый завершённый этап — отдельный коммит и немедленный push.
5. **Живая проба.** Пользователь заполняет `.env` локально, без передачи ключей
   в чат. Проверить доступность модели, реальные квоты и 2–3 короткие задачи
   на разных проектах. Без живой проверки не утверждать, что пользовательские
   ключи и их квоты проверены. Публикация релиза — отдельный этап.

Для будущего обновления потребуется заменить и перезапустить агент, обновить
расширение и вкладку AI Studio. Gate обновлять и перезапускать не потребуется.
Для этого плана агент не компилировался: текущий комплект не содержит новой функции.
При реализации пользователю будет предоставлен готовый EXE в Windows-комплекте;
самостоятельная сборка для установки готового комплекта не нужна.

## Что сознательно оставляем за рамками

Нет самостоятельного редактирования файлов субагентами, рекурсивного делегирования,
обмена сообщениями между субагентами, выбора моделей в интерфейсе и новой панели
управления ключами. Нет автоматического включения биллинга или перехода на платный
тариф. На первом шаге нужен рабочий путь «текстовая задача → ответ в исходный чат».
